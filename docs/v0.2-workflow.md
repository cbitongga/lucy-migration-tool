# Version 0.2 workflow and records

The v0.1 feature/question/defect record shapes in record-format.md still apply.
The limitations there describe that older release; this document and README.md
are authoritative for the new capabilities. All put operations are complete
record replacements. Contract edits invalidate earlier work/evidence. Stage and
review results are evidence, so they do not recursively invalidate contracts.

## Agent execution

Seven native roles are provided: migration-coordinator, migration-discovery,
migration-planning, migration-backend, migration-ui, migration-verification and
migration-review. The coordinator runs in the main client session and calls
native subagents. MCP is optional: the same operations are available in the CLI.
The Python engine does not create hidden paid model calls or background AI loops.

The coordinator repeatedly asks next-action, sends a bounded task to the selected
role, checks durable output, and advances only when the engine's gates permit it.
It stops for missing evidence or a repeated failed task, recording a resume point.
The generated agent definitions do not establish an OS sandbox or a separate
trust boundary. User/client tool policies still govern actual access.

## Map and file accounting

`map` stores a source graph; `list map_nodes`, `list map_edges`, and
`list map_gaps` paginate it. `map --format json` exports the full graph;
`map --format mermaid` exports a limited visual projection. Limits are stated in
the projection. Raw/inferred relationships carry evidence/confidence labels.

Every in-scope source file needs a reviewed disposition for acceptance readiness:

```json
{
  "id":"SourceInvoice",
  "source_ref":{"root":"legacy","path":"Invoice.cs"},
  "source_sha256":"ACTUAL_CURRENT_FILE_SHA256",
  "disposition":"feature",
  "feature_ids":["F1"],
  "reason":"Specific evidence tying this source to F1",
  "reviewed_by":"Actual reviewer or evidence provenance"
}
```

Other dispositions: support, generated, out_of_scope. Every disposition needs
an explicit reason; they must not hide difficult code. Source edits stale the
review. File accounting is not proof of complete business-feature discovery.

## Type mappings and plans

```json
{
  "id":"DecimalMapping",
  "feature_ids":["F1"],
  "source_type":"C# decimal",
  "target_type":"Java BigDecimal and a React string",
  "semantics":"Document the actual range, scale, rounding, nullability and serialization rules here",
  "scenario_ids":["BoundaryCase"],
  "source_refs":[{"root":"legacy","path":"Invoice.cs"}]
}
```

Each type-mapping scenario is added to the feature's verification requirements.

```json
{
  "id":"PlanF1",
  "feature_id":"F1",
  "architecture":"Evidence-backed framework choices, folder boundaries, persistence and error contracts",
  "type_mapping_ids":["DecimalMapping"],
  "required_commands":["build-java","test-java"],
  "implementation_roles":["backend","ui"],
  "confirmed_by":"Actual user decision or cited existing policy; never fabricate"
}
```

A plan requires nonempty type mappings and build/test commands. Frameworks in
examples are illustrative. Source models alone are not an approved DB schema.

## Backend/UI stage evidence

After editing the target within the coordinator's feature lease:

```json
{
  "id":"BackendF1",
  "feature_id":"F1",
  "role":"backend",
  "summary":"Concrete implementation work completed and any known limitations",
  "output_refs":[{"root":"target","path":"src/Invoice.java"}]
}
```

The engine captures current source and output hashes. It will not mark a planned
feature implemented until its required backend/UI stages have current outputs.
A stage is not a build or parity pass. After contract changes, use release with
the current lease token and obtain a new packet/claim; do not wait for lost work.

## Configured commands

The manifest's optional commands object maps names to executable argv arrays:

```json
{
  "build-java": {
    "argv":["javac","-d","build","Invoice.java"],
    "cwd_root":"target",
    "purpose":"build",
    "timeout_seconds":120,
    "max_output_bytes":1000000,
    "expected_artifacts":[{"root":"target","path":"build"}]
  }
}
```

This is the value of commands, not a full manifest. Purposes are build, test,
capture, setup. Build commands MUST declare expected artifacts; outputs must
exist and their hashes remain current. Files/directories are supported. A
changed/deleted binary stops the build pass counting even if its output folder
is excluded from source scanning. Exclude genuine build output folders in
exclude_dirs so compiler outputs do not stale source code fingerprints.

Placeholders supported in argv strings: {python}, {tool}, {control}, and
{root:ROOT_ID}. They are expanded as array entries, never executed through a
shell. Commands inherit the process environment. Do not embed secrets in the
manifest or put production commands here. Use the configured test scope.

`command NAME` starts a background worker; `command-status JOB_ID` polls it.
`command NAME --wait` is convenient for scripts. Logs live under
.migration/jobs/JOB_ID/. Restart does not replay side effects. Expired queued or
running records become interrupted via recover. The stdout/stderr byte limit
is combined; crossing it terminates the child and cannot produce a pass.

Add important external fixture files, database files, and dependency binaries to
manifest evidence_inputs. They are hashed for verification freshness. SQLite
WAL files are included when present. This is file tracking, not attestation that
a remote service runs the declared build. Record real deployment/build evidence.

## Typed observation scenarios

```json
{
  "id":"DatabaseCase",
  "feature_id":"F1",
  "adapter":"observation",
  "dimension":"database",
  "legacy_command":"capture-old-db",
  "target_command":"capture-new-db",
  "legacy_observation_sha256":"ACTUAL_CHARACTERIZED_OBSERVATION_DIGEST"
}
```

Both commands must have purpose capture and must produce exactly this envelope
on stdout (logs go to stderr):

```json
{"schema_version":1,"dimension":"database","observations":{"example":{"type":"text","value":"9007199254740993.10"}}}
```

Dimensions supported by this generic contract: ui, database, integration,
performance. An adapter must actually measure the declared dimension. Tagging
arbitrary output as database is not database verification; review its capture
program and fixtures. Empty observations, duplicate keys and nonfinite JSON
numbers are rejected. Integer, decimal, string, boolean and null remain distinct.
Object key ordering is ignored for typed snapshots; arrays, duplicates, strings
and decimal scale remain exact. No user-visible behavior is silently normalized.

Capture legacy output first using its command, inspect it, then calculate the
oracle with `observation-digest FILE --dimension database`. That digest is a
reviewed fixture expectation, not an AI estimate. A changed legacy baseline
blocks the comparison even if target output happens to match it.

The SQLite adapter is adapters/sqlite_capture.py. It opens the database read-only
and reads schema plus typed rows within a transaction; physical row order is
ignored while duplicates are retained. Use --table to explicitly scope tables.
Other databases require their own real capture adapter. Exercise transactions,
rollback, concurrency and external side effects in separate controlled scenarios.

The browser adapter is adapters/browser_capture.cjs and requires installed
Playwright plus Chromium. It uses a fresh browser context, explicit test origins,
configured actions, and observations. Supported actions: goto, fill, click,
press, select, check, wait. Observations: text, value, count, visible, attribute,
path and screenshot_sha256. Non-count element observations require one match.
See examples/invoice/control/browser-case.json. Additional exact test origins
may be listed in allowed_origins; other network requests are blocked. Login,
seeding, state resets, per-role workflows, and visual stability need app-specific
configuration. Browser binaries are not bundled or automatically downloaded.

## Optional Roslyn adapter

adapters/roslyn contains a .NET 8 console project using the compiler assemblies
shipped in the installed SDK. Its source has NOT been compiled in this environment.
Build it with your SDK, then configure a capture command invoking its DLL with
--root PATH --root-id ROOT_ID. Supply matching --reference DLL paths and --define
symbols where required. Include dependency files in evidence_inputs.

After a successful current command job, call semantic-import JOB_ID. Every
semantic node's source hash is checked against registered source roots. Run map
again to include the current declarations and resolved call edges. Diagnostics
and unresolved bindings are retained. The adapter does not evaluate an entire
MSBuild solution, include generated files automatically, or prove runtime parity.

## Review and acceptance

```json
{
  "id":"ReviewF1",
  "feature_id":"F1",
  "reviewer":"Actual reviewer identity/role",
  "summary":"What was inspected and the limits of this review",
  "issues":[],
  "evidence_refs":[{"root":"legacy","path":"Invoice.cs"},{"root":"target","path":"src/Invoice.java"}]
}
```

The engine binds a review to current source/target/contract evidence. Review
judgment cannot replace failing builds or scenarios. Resolve issues through a
new reviewed record, not by altering test expectations. Preserved bugs remain
in the defect registry; proposed fixes follow acceptance as separate changes.

Per-feature verification measures declared dimensions. ready_for_acceptance also
requires current successful required commands/artifacts, current clear reviews,
reviewed source-file accounting, a current map, no missing tracked inputs and no
unanswered questions. Exclusions and map uncertainty remain disclosed.
complete stays false: this system does not prove unobserved behavior equivalent.
